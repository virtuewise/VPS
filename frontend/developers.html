PROVIDER SDK ? V1

Build and install a provider

Packages are declarative, versioned, signed and installed by a node administrator.

API 1.0.0
1

Implement the contract

Implement list_vms, list_switches, host_monitor, create_vm and vm_action. Return JSON-compatible normalized objects.

2

Declare capabilities

Use only the capabilities the provider needs: inventory.read, host.metrics.read, vm.create, vm.power, vm.delete and vm.console.

3

Build and sign

Build a .vwpkg archive and sign its SHA-256 digest with an Ed25519 publisher key. Keep the private key offline.

4

Install and enable

Install against an administrator-managed trust store. New versions are disabled until explicitly enabled.

Build and sign commands

PowerShell ? run from agent directory
.\.venv\Scripts\python.exe provider_sign.py keygen --key-id publisher-2026 --private-key publisher-private.key --public-key publisher-public.key
.\.venv\Scripts\python.exe provider_sign.py build ..\examples\providers\sample sample.vwpkg
.\.venv\Scripts\python.exe provider_sign.py sign sample.vwpkg --key-id publisher-2026 --private-key publisher-private.key --output sample.sig.json

Install and activate on a Linux node

Bash ? run on the rootless-Docker node
cd /opt/virtuewise/VPS/agent
export VPS_PROVIDER_REGISTRY=/var/lib/virtuewise/providers
export VPS_PROVIDER_TRUST_STORE=/etc/virtuewise/trusted-providers.json
export VPS_PROVIDER_SANDBOX=docker
export VPS_PROVIDER_SANDBOX_IMAGE=python:3.11-slim@sha256:REPLACE_WITH_VERIFIED_DIGEST
python3 providerctl.py install sample.vwpkg --signature sample.sig.json --trust-store "$VPS_PROVIDER_TRUST_STORE"
python3 providerctl.py enable org.example.provider.sample
python3 providerctl.py check org.example.provider.sample
python3 providerctl.py events

Lifecycle commands

providerctl.py listproviderctl.py eventsproviderctl.py disable PROVIDER_IDproviderctl.py rollback PROVIDER_IDproviderctl.py uninstall PROVIDER_ID

Runtime requirement: third-party providers require rootless Docker and an immutable, digest-pinned Python image. The worker has no network, a read-only root filesystem, dropped capabilities, non-root UID, and resource limits. This runtime currently targets Linux nodes with rootless Docker; the Windows Hyper-V provider remains built in. Test-only subprocess mode is not a production sandbox.

Install the MCP server

PowerShell
cd mcp-server
py -3.11 -m venv .venv
.\.venv\Scripts\pip.exe install -e .
$env:VPS_MCP_API_URL = "https://your-control-plane.example"
$env:VPS_MCP_READ_TOKEN = "YOUR_LONG_RANDOM_READ_TOKEN"
.\.venv\Scripts\virtuewise-vps-mcp.exe

Use the same randomly generated VPS_MCP_READ_TOKEN in the control-plane environment. Treat it as an administrator secret: it currently grants infrastructure-wide read-only access, not per-customer delegated scopes. Remote API URLs must use HTTPS.

HTTP API

Control-plane API reference

Open the interactive OpenAPI reference on your running instance for request and response schemas. The following routes summarize the stable integration surface.

GET/api/healthControl-plane health
POST/api/auth/loginCreate a signed session
GET/api/vmsList VMs visible to the signed-in user
POST/api/vmsQueue VM provisioning; returns HTTP 202
GET/api/jobs/{job_id}Read provisioning job state
GET/api/nodesList registered compute nodes
POST/api/scheduler/placementPreview resource-aware placement
GET/api/integrations/mcp/*Dedicated read-only integration API

Authentication rules

  • Browser and REST sessions use the signed HttpOnly session cookie.
  • State-changing session-authenticated requests require the matching X-CSRF-Token.
  • Administrator operations require the administrator role; VM operations are constrained by ownership and quotas.
  • MCP routes use a separate bearer token named VPS_MCP_READ_TOKEN and are read-only.
  • Do not embed node-agent credentials or publisher private keys in browser code.
SECURITY AND RELEASE STATUS

Know the boundaries

Implemented

  • Strict versioned manifests and capability allowlist
  • Ed25519 package signatures and SHA-256 integrity checks
  • Administrator-controlled trust store and revocation
  • Typed worker protocol and per-operation capability checks
  • Rootless Docker sandbox profile for third-party code
  • Install, upgrade, disable, rollback and uninstall lifecycle

Still required before public production

  • Real Hyper-V and KVM host acceptance testing
  • Independent security review and container escape assessment
  • Privileged virtualization broker separated from plugin workers
  • Per-customer delegated authorization for MCP
  • Production deployment, backup, monitoring and incident procedures

VirtueWise VPS remains an early-development project. Automated tests do not replace real-host validation or an external security review. Never expose the development API or node agent directly to the public internet.
